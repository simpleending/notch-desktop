# Performance audit — October 18, 2026

The measured problems justify targeted fixes before another native rewrite. Tests ran on Windows x64 with Node 24.14.0 and the packaged Electron app. Samples use warm filesystem caches; these are focused measurements, not universal speedup promises.

| Area | Evidence | Decision |
| --- | --- | --- |
| CLI grep | A 1,000-file miss took 1,005 ms; shell execution blocked the event loop for roughly 300 ms. The no-match fallback could search ignored files. | Reuse the desktop's asynchronous, shell-free ripgrep path. Preserve no-match/error distinctions, cancellation, nested fallback ignores and glob matching. ripgrep is already Rust. |
| Indexed search | fff is already a native Rust dependency. A regression caught a filename index failing to discover a new file. | Explicitly watch filename indexes and rescan invalidated indexes. Retain canonical ignore checks and compatibility routing. A second search implementation would add parity risk. |
| Code intelligence | Compiler and symbol commands synchronously blocked their caller. Windows could not reliably execute the npx shim; file-only TypeScript checks discarded project settings. | Run existing compilers asynchronously, honor cancellation and use the installed project's compiler/configuration. Native language tools already do the expensive work. |
| Token estimates | The old implementation allocated an array for every character. Synthetic 1/8/32 MiB estimates took 17/101/1,224 ms; the single-pass implementation measured 17/101/303 ms. Counts remain identical, including Unicode. | Ship the allocation fix. For unusually large histories, measure moving this work off the main thread next. A native implementation may help this scale, but model runtimes already perform the actual model-specific tokenization. |
| Windows shortcut projection | A normal app and an explicit test profile competed to rewrite shared shortcut icons. Ten seconds in the isolated profile consumed 7.41 CPU seconds with main-loop p99 delay 219 ms; after isolation, 0.27 CPU seconds and 26 ms. The normal app alone used 0.016 CPU seconds over a separate five-second idle sample. | Explicit profiles keep their window icons but skip shared shortcut scans, writes and watchers. This was an isolation bug, not evidence that all normal app idle time is expensive. |
| Hardware/RAM/VRAM discovery | Original cold discovery took 1,324 ms. The subsequent Rust implementation measured 86.5 ms median versus 586.0 ms for the same PowerShell probe in serial fresh-process pairs (6.77×); p95 94.8 versus 637.0 ms. | Implemented a small Rust helper querying the same WMI/DXGI fields, retaining the PowerShell fallback and RAM-only failure behavior. Exact sizing and model plans remain outside the helper. See the follow-up below. |
| CLI startup | Three fresh-process samples per case after warmup: help 84 ms and version 96 ms medians. | No rewrite justified by this result. These commands do not measure a complete inference startup. |
| Renderer | Idle CPU sampling was overwhelmingly idle. The full Electron/Chromium process tree still has a material memory baseline. | No measured reason to rewrite UI components in Rust. A different desktop shell would be a separate architecture project with much wider compatibility costs. |

Recommended order: ship these fixes and the narrowly scoped hardware helper; investigate background processing for exceptionally large histories if users encounter them. Keep file search on fff/ripgrep and model inference/tokenization on the existing native runtimes. Do not start a broad UI, networking, database or orchestration rewrite from these measurements.

The source suites passed 659 CLI tests and 220 desktop tests, both typechecks, and 17 fresh CLI package checks including a dependency audit. The frozen CLI also read a real local Qwen3 0.6B receipt and recovered it after a process restart, with its model unloaded afterward. A 16K context was used; 4K/8K correctly rejected the complete tool catalog as too large. This does not establish compatibility with every model or backend. Packaged UI verification receipts are recorded separately in the release audit.

Local evidence is retained under ignored `analysis/`: `audit-search-before.json`, `audit-search-after.json`, `transcript-performance-0122*.json`, `hardware-performance-0122.json`, `cli-startup-0725.json`, `ide-performance-0121.json`, `ide-performance-0122.json`, and their CPU profiles. The first post-fix search sample overlapped other checks; use the final serial sample for timing comparisons. Returning IDE launches were single samples (5.4 s before, 7.0 s after under different concurrent load), so no startup improvement is claimed.

Method follows the current [Electron performance guidance](https://www.electronjs.org/docs/latest/tutorial/performance), [Node performance hooks](https://nodejs.org/api/perf_hooks.html), and [asynchronous child-process API](https://nodejs.org/api/child_process.html#child_processexecfilefile-args-options-callback). Physical hardware beyond this Windows machine, macOS/Linux, and paid provider inference are outside this audit.

## Rust hardware-helper follow-up

Included in CLI 0.7.26 and desktop 0.1.23. See [source and build notes](../vendor/notch-cli/native/windows-hardware/README.md).

The 330,240-byte executable reads the same physical-memory capacities, maximum GPU-usage counter and DXGI dedicated capacity as PowerShell. It never substitutes installed RAM for available RAM. `min(os.freemem(), process.availableMemory())` is still read for every hardware-discovery call. The IDE's forced refresh before local turns is retained; CLI download/load checks now explicitly bypass the five-second browsing cache as well. Failed refreshes invalidate the cache. Timeouts, malformed/unsupported JSON, missing helpers and probe failures retain the existing PowerShell/RAM-only fallback. Reserves, model weights, context/KV calculations and Colibri checkpoint planning are unchanged.

Final benchmark: ten serial alternating pairs with a fresh subprocess for each sample; the first pair is recorded separately, the remaining nine provide median/p95. This measures warm Windows/provider caches, not cold boots. The first observed invocation of the final Rust binary was 598.8 ms versus 779.2 ms for PowerShell. Installed RAM (34,359,738,368 bytes) and dedicated capacity (16,993,579,008 bytes) matched exactly across all pairs. Time-varying GPU usage differed by at most 6 MiB between paired observations. OS-usable RAM remained 16,802,189,312 bytes; the larger installed-RAM number never inflates the loading budget.

Verification: 675 CLI tests, 222 desktop tests, both TypeScript checks, two Rust tests and Clippy with warnings denied passed. Boundary tests compare native/fallback fit and context decisions; low-memory tests block CLI loading and IDE turns after memory pressure changes. Nine package checks exercised actual native execution, forced PowerShell fallback, complete failure, cache hits and forced refreshes across the npm tarball, built IDE core and Electron ASAR/unpacked executable. No model was loaded for this follow-up. Windows x64 is measured; ARM64 and physical multi-GPU hardware are not validated. The changed GitHub release workflow was syntax-checked locally, not executed remotely.

Receipts: `analysis/rust-hardware-benchmark.json`, `analysis/rust-hardware-packaging.json`, `analysis/rust-hardware-ide-tests.log`, and the workspace's `rust-hardware-cli-tests.log`.
