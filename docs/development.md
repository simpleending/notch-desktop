# Developing notch desktop

Public development repository for a free desktop coding workbench, with local open models first and optional OpenRouter, OpenAI and Anthropic API keys.

The session adapter runs the CLI provider/tool loop, streams assistant/tool messages, requests exact tool approvals, cancels active work and saves conversation and undo state. The Windows x64 release uses an Electron workbench with notch's dark/light interface. Other platforms, signing, paid-inference coverage and performance parity remain outside the verified Windows scope.

```sh
npm ci --ignore-scripts
npm test
npm run models
npm run inspect:upstream -- --installation "/path/to/installed/app" --out analysis.json
npm run build:core
npm run build:prototype -- --installation "/path/to/installed/app"
```

On Windows x64, `npm run package:windows -- 0.1.2` creates the unsigned release installer; a version such as `0.1.2-preview.1` creates a separate preview. It uses pinned electron-builder 26.15.3 and its cached Windows resource editor. The installer launches notch directly, without a separate update launcher, and keeps application data on uninstall. `npm run verify:settings -- /path/to/Notch.exe` visits all visible settings sections in an isolated profile. The package check verifies the secondary artwork, product labels and renderer imports before creating an installer.

Node.js 22.19+ is required. The desktop uses CLI 0.7.5 for guided Hugging Face installs and a vendored CLI harness for agent turns. The model picker exposes only specific IPC methods. Desktop API keys are validated with their provider and saved through Electron’s asynchronous OS encryption; no secure store means session-only keys. Keys are not returned to the renderer, included in conversation state, or forwarded to unrelated child processes.

Redistributing inherited workbench components requires applicable modification and redistribution rights. The port integrates through the inspected Electron workbench and agent SDK boundary. See [the upstream analysis](upstream-analysis.md). Generated upstream archives, extracted application files, credentials and machine-specific analysis are excluded from Git. Third-party notices must remain with any redistributed components.

The port replaces application branding and provider routing. Actual open model names and repository IDs remain accurate, including Qwen models when selected from the model dropdown. A repository creation date is used for newest-first ordering; it does not establish model capability or quality.

MLX is beta pending Apple hardware verification. Performance parity and macOS/Linux desktop packaging remain unverified.

The shared CLI core source is included under `vendor/notch-cli` with its license, so the desktop harness can be rebuilt and inspected without a private checkout. The vendored core includes approval/session extensions and subsequent model/context/undo fixes; the separately published installer CLI is 0.7.5. Agent tool restrictions apply independently of global full access.

Each model runtime uses its own tokenizer and chat template. Guided GGUF installation selects checksum-verified native Ollama tool profiles from the imported architecture/template, then verifies both a structured tool call and a tool-result round trip before saving a selection. Native context limits come from Ollama model metadata, revision-specific MLX text configuration or the OpenRouter model catalog; the desktop passes those limits through its agent budget and native request. Older MLX installations lacking metadata retain an 8K ceiling until reinstalled. Token estimates before a request remain approximate; displayed usage uses provider counts. Arbitrary model repositories may fail tool validation. Apple MLX inference and paid hosted inference still require hardware/credential verification.

After installing the public Hugging Face Qwen3.5 4B and Gemma4 E2B models, run `node scripts/verify-model-compatibility.mjs /path/to/installed/Notch.exe /path/to/report.json`. It launches an isolated profile, exercises real read-only tool-result requests with both models, verifies their distinct native architecture/context metadata and compares the reported budget with the runtime allocation. It unloads the test models afterward.

Initial live harness verification used the installed Hugging Face Qwen3.5 4B model: it read a test, requested write and shell approvals, created a correct finite-number addition function and ran the test successfully. The model was unloaded afterward. An earlier native prototype started with a separate user-data directory; the complete lowercase rename is being validated against inherited runtime/schema assumptions.

The lowercase SVG [wordmark](../assets/notch-wordmark.svg) has [dark](../assets/notch-wordmark-dark.svg) and [light](../assets/notch-wordmark-light.svg) variants. The landing page uses two actual light-mode captures of the installed Windows app: a TypeScript editor and the model picker. Screenshots demonstrate the interface; the verification record describes the tested workflows.

The first-launch popup uses a quiet notch welcome and workflow screen, with dark/light appearance, keyboard navigation and the notch wordmark. Startup and onboarding sounds are removed. Setup completion uses the existing validated IPC path and preserves workspace data. Setup appearance now carries into the workbench. Run `npm run verify:setup` after building to check first launch, both appearances, keyboard navigation, completion and restart using a temporary profile.

The workbench uses notch's neutral dark/light palette, wordmark and application icons. The home screen has a small heading, project link and composer. Code/Chat switches and panel launch actions use plain text controls; inherited trees, doodles, heatmaps, pet/mobile promotions and decorative backgrounds are removed from these surfaces. Shared menus, dialogs, editor gutters, file panels and terminal colors follow the same palette. Appearance keeps reading font, text size, interface scale, content width, file icon, terminal and language preferences. `npm run verify:skin` checks the UI in a temporary profile and opens real fixture files; its folder-picker selection is controlled by the test, so it does not test the OS file dialog. These UI checks do not establish production readiness or performance parity.

Menus use softer corners, restrained selection colors and the locally bundled Manrope variable font, including setup. Appearance selects use Chromium's native customizable select, retaining keyboard selection and preference handlers. The font's [OFL notice](../assets/fonts/Manrope-OFL.txt) is included in the application.

Local file-panel search and desktop agent search share [fff](https://github.com/dmtrKovalenko/fff)'s pinned `@ff-labs/fff-node` 0.11.0 library in an Electron utility process. Two indexes are reused and released after one minute idle or shutdown. Filename-only indexes remain lightweight; agent searches enable bounded content caching lazily. Agent glob uses the native index, with canonical file membership and pattern checks. Literal grep uses fff only when the selected corpus is compatible UTF-8 source text; full regexes, grep glob overrides, explicit files, larger files and unsupported formats use the bundled unmodified ripgrep 15.2.0 executable asynchronously. No model tool performs native indexing on the UI thread. Search paths and results remain inside the selected workspace. Mutating tools invalidate indexes before and after execution; external file and ignore edits trigger rescans. The [MIT notice](../assets/notices/fff-LICENSE.txt) and ripgrep/PCRE2 notices are bundled. Remote SSH search and composer attachment search are unchanged; Windows is the tested platform.

Workspace grep and glob honor `.gitignore` without requiring Git metadata. Wildcard glob searches omit hidden paths and dependency/build outputs; explicitly selecting a directory or file remains available. See [search performance](search-performance.md) for compatibility routing and regression coverage. `npm run verify:search -- <installed-executable> <report.json>` drives the real packaged composer and native utility process using a deterministic provider fixture; `verify:agent` separately validates real local inference, approvals and continuation.

`npm run typecheck` validates the shared harness with strict TypeScript settings. `npm run verify:agent` requires the installed Hugging Face test model and an Ollama server on localhost:11436. It uses a fresh profile and real scratch files, sends the task through the composer, clicks native approvals, independently tests the generated implementation, validates execution/context state, resumes after restart and cancels a pending write without changing the file. The test unloads its model afterward. The [Windows verification record](release-readiness.md) distinguishes verified workflows from remaining coverage.

The model picker has Installed, Hugging Face and OpenRouter tabs, search, arrow-key navigation and explicit context selection. Hugging Face searches compatible GGUF/MLX repositories with pagination; installation revalidates metadata and estimated memory. Its token form is optional and dismissible; public guided downloads need no account. Its metadata is cached for six hours. OpenRouter's public text-model catalog can be browsed without a key; running a model requires a validated key, and unsupported agent models are disabled with a reason. The catalog shows newest-first ordering and per-million-token pricing. Official provider marks are bundled unchanged. Cloud selection never happens as a fallback from a failed local request.

Automatic local context rechecks available RAM and VRAM before each turn, preferring a GPU-resident limit up to 128K when model metadata and estimated memory allow it. It falls back to 8K or a smaller fitting limit; 256K is an explicit option when supported. Options are capped by the model’s advertised context and a conservative FP16 KV-cache estimate; hybrid attention is deliberately overestimated. The running model’s own allocation is accounted for when refreshing its limits. These are memory estimates, not guarantees. OpenRouter defaults to 32K or the model’s lower published limit, with larger published contexts selectable independently of device RAM. Every agent request reserves output space, instructions/tool-schema overhead and safety margin. At 80% of the remaining history allowance, the selected model summarizes older turns; the current user task and full tool-call/result chain remain intact. A model-specific failure circuit falls back to deterministic summarization. Original transcripts are saved in the profile’s `notch-sessions/<id>.archives` before compaction. Provider token counts calibrate subsequent checks; oversized current requests fail clearly rather than silently truncating them. The native context inspector displays the latest provider request’s actual counts.

`npm run verify:undo -- <installed-executable> <report.json>` drives native composer writes, matching review entries, restart, dry-run conflict checks, selected-turn restore and the actual Undo confirmation button. Checkpoints are private atomic files bound to workspace identity; restoration transactions remain retryable after partial failure. Only built-in write/edit/patch actions are captured. Unverified crash windows and later manual edits fail closed.

`npm run verify:recovery -- <installed-executable> <report.json>` adds forced process-tree termination, interrupted atomic chat/checkpoint saves and a partially completed file restore. It sends Windows shutdown/restart, logoff, critical-close and canceled-session messages only to the test window after checking its owning process. Each restart checks SQLite integrity and foreign keys, the saved transcript, checkpoint identities and native Undo. The test uses a temporary profile/project and mocked inference, so memory availability does not affect recovery coverage; local model metadata must be available. It never shuts down or logs off the computer. Targeted messages exercise the Windows application path; a complete OS shutdown and physical power loss still require separate testing.

`npm run verify:unsaved-shutdown -- <installed-executable> <report.json>` verifies that canceling quit preserves a real unsaved editor buffer and leaves discovery usable, then saves the edited file and exits cleanly. Process cleanup in these checks uses creation times to exclude unrelated processes after Windows reuses a PID.

Plugin catalogs are regenerated only during packaging, after branding. Startup retains per-file SHA-256 verification; tamper tests cover changed and unlisted files. Discovery uses a local manifest/component-path validator rather than launching an unavailable worker. Validation does not execute plugin commands or prove third-party code is trustworthy.

`npm run verify:shutdown -- <installed-executable> <report.json>` tests fourteen Windows startup/exit cases in isolated profiles: early quit, the setup Close button, completed setup, returning-window closes, delayed application-discovery IPC and loaded plugins. It checks process exit, owned descendants, main-process shutdown diagnostics and SQLite integrity. Window-close cases select the existing quit preference rather than minimizing to the tray. Discovery cancellation starts only after exit confirmation; cancelling a quit keeps discovery usable. Plugin startup is cancelled and joined before its registries are cleared. Catalog reads can be interrupted only after exit confirmation; the next launch still verifies the complete catalog. Read-only app/plugin/model discovery is cancelled inside the IPC tracker, while configuration writes keep their normal completion path. Renderer confirmation waits for readiness, and setup-only windows do not join the workbench acknowledgment barrier.
